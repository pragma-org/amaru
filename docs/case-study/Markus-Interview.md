# Interview - [Markus Gufler](https://github.com/gufmar), SPO and Cardano ecosystem contributor


### Next steps discussed:

Markus wants to replace some of his relay nodes with Amaru nodes. We will provide him with the information and documentation needed to configure Amaru as soon as the [Minimum Viable Relay v11](https://github.com/pragma-org/amaru/milestone/24) is ready.

### Overall documentation discussion:

https://developers.cardano.org/docs/operators/ should serve as reference documentation for both Haskell and Amaru nodes, it would be node language agnostic, and use a tabbed interface.

Documentation should be informative rather than "copy paste-ready", as new SPOs need to understand what they are doing. A proper balance needs to be found between practicality and knowledge.

Mithril bootstrap with ledger state (--include-ancillary) should not be used for block producer as the network currently lacks a sufficient number of Mithril signers to guarantee the reliability of the process.

PeerSharing is not ready for use at the moment, as it propagates the internal node IPs when behind NAT. In reality, peers discovered via PeerSharing are either already known from on-chain data or simply not reachable.

There is no documentation available on configuring a resilient node pool. The best current solution involves having a ready-to-use BP node, updating its configuration file and restarting it when necessary. But this process takes several minutes.
-> A syscall flag to switch the BP node state from "waiting" to "producer" is currently lacking.
However, Markus notes that he has never needed to activate his secondary node, as the Haskell node is pretty stable.

### Operational needs from Markus’s setup perspective:

- The ability to have a "standby" BlockProducer node that can switch to producer state without restarting.

- Possibility to easily gather some metrics that are needed for the [openBlockPerf](https://developers.cardano.org/docs/operators/monitoring/monitoring-openblockperf/#what-does-it-observe) project (they are currently generated by parsing the Haskell node logs):
	- Distinct propagation stages in millisecond precision for :
		- Time until a relay node first hears about the new block header.
		- Time while the relay node requests the block body from peers.
		- Time until the block body download completes.
		- Time until the local node validates and adopts the block.


### Deployment reality:

The deployment setup is VM-based, using custom bash script and cntools. Monitoring is done with [PRTG](https://www.paessler.com/fr/prtg)
